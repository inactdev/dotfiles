# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Nix/home-manager entry points: `flake.nix` (hosts: `darwinConfigurations.personal-mac`, `homeConfigurations.home-linux`/`.codespace-personal`/`.codespace-work`), `configuration.nix` (Darwin-only: system + Homebrew), `modules/*.nix` (packages, dotfile symlinks, launchd agents - composed per host, see the next bullet). Apply with `./run.sh rebuild` (see `./run.sh help`) on personal-mac/home-linux, `install.sh` on Codespaces (see below). `nix eval --impure --expr '(builtins.getFlake (toString ./.)).darwinConfigurations.personal-mac.config...'` (swap in `.homeConfigurations.home-linux.config`/`.codespace-personal.config`/`.codespace-work.config` for the others) lets you check that an option evaluates without building or switching anything - `nix build`/`home-manager switch` for a Linux target will fail on a non-matching-arch machine with a platform-mismatch error, which is expected; eval succeeding is the real check. The two `codespace-*` outputs additionally require `--impure` (they read `USER` from the environment - see the next bullet).
- `home.nix` no longer exists: it's split into `modules/core.nix` (cross-host CLI tooling, every host imports this), `modules/desktop.nix` (personal-mac + home-linux only: ghostty, fonts, git identity, the local-machine Claude settings variant), `modules/mac.nix` (personal-mac only: herdr, launchd), and `modules/codespace.nix` (the Codespaces-only delta: the Claude Code package, and the two things that still vary by posture - which Claude settings file, and the `cc` alias - via a `posture` extraSpecialArg). `flake.nix` composes these per host through a small `homeModules` helper that wraps them in `lib.mkMerge`, not Nix's `imports` - **this is load-bearing, not a style choice**: `imports` puts each file at its own position in the overall module tree, which changes the *order* home-manager concatenates any list-typed option (`home.packages` is the one that actually bit this) even when every file's own contribution is byte-identical, silently producing a different derivation hash for personal-mac/home-linux than before the split. `lib.mkMerge` inside one function-module reproduces the original single-`home.nix` shape exactly - verified by comparing `nix eval` drvPaths for personal-mac/home-linux before vs. after the module split (byte-identical). Extending a host's module set means adding to that host's `homeModules [...]` list in `flake.nix`, not switching it to `imports`.
- Most of `home/**` is symlinked into `$HOME` via `mkOutOfStoreSymlink` in `modules/core.nix`/`desktop.nix`/`mac.nix` - editing the symlinked path IS editing the repo; nothing needs re-copying.
- Herdr plugins (`herdr plugin ...`) cannot host a long-running/daemon process: startup hooks are one-shot and must exit, and `[[panes]]` are user-facing terminal surfaces, not hidden background workers. Anything that needs to react continuously (e.g. polling `herdr agent explain` for detection-rule changes) belongs in an external script driven by a home-manager `launchd.agents` entry, not a plugin - see `home/.local/bin/herdr-agent-handoff-marker` and its `launchd.agents` block in `modules/mac.nix` for the pattern. Verify that script only with `sh home/.local/bin/herdr-agent-handoff-marker.test.sh`, which runs it against a mocked `herdr` on a hermetic PATH: never run it (or any `herdr tab rename`) against the live daemon, which would repaint the owner's real tabs. The hourglass mark is scoped to crewmate task tabs only (label convention `fm-<id>`, matching firstmate's own crewmate spawn labeling in the firstmate repo's `backends/herdr.sh`) - herdr's detection rule is pure content screen-scraping with no notion of tab role, so the marker script itself is the only place that knows a primary/secondmate tab must never be marked, and it self-heals a stray mark found on a non-`fm-*` tab regardless of that tab's handoff state.
- `run.sh` supports three hosts: `personal-mac` and `home-linux` (both Nix + home-manager) and `work` (plain Homebrew, no Nix - see the work-host section in `README.md`). With no explicit host/flags, `run.sh` asks once via an interactive menu; a "home" answer auto-detects Mac vs Linux from `uname -s` rather than asking, and a "work" answer on Linux fails immediately (there is no work-linux host - see the codespaces bullet below). The answer is remembered in `.dotfiles-host` (gitignored, per-clone); `./run.sh choose` re-asks. `run.sh` sources cleanly (see the `BASH_SOURCE` guard at its tail) so `run.test.sh` can call its functions directly against a mocked `uname` - run with `bash run.test.sh`. Everything for the work host lives under `work/`: `work/bootstrap.sh` does the installing/linking/configuring and is idempotent, `work/Brewfile` is the exact package manifest, `work/zshrc` is the real `~/.zshrc` for both the work Mac and Codespaces' work posture (self-detects Homebrew vs. apt at runtime rather than existing as two files), `work/claude-settings.json` is derived from `home/.claude/settings.json` - `hooks`/`skipDangerousModePermissionPrompt` stripped, plus the standing work override pinning `model`/`effortLevel` to opus/xhigh (re-derive with the steps in README.md after editing the source file; the `jq` command alone clobbers the override) - and is likewise shared with Codespaces' work posture. `work/bootstrap.sh` itself is sourced (not copied) by `work/codespace-bootstrap.sh` - see the codespaces bullet below - for every function with nothing macOS-specific about it (`link_with_backup`, `install_symlinks`, `install_zshrc`, `install_claude_settings`, `configure_git_identity`, `configure_git`, `print_git_gh_pending`); only `install_ghostty_symlink` stays Mac-only within that shared set (ghostty is meaningless in a container), called separately from `install_symlinks` in `work/bootstrap.sh`'s own `main()`. A change to any of those shared functions affects both hosts - check `work/codespace-bootstrap.test.sh`'s "same function object" tests before assuming a hand-copy needs updating too; there isn't one. Verify `work/bootstrap.sh` only with `sh work/bootstrap.test.sh`, which mocks `brew`/`defaults`/`killall`/`gh` on a hermetic PATH and a scratch `$HOME` - never run the real script against this machine's real Homebrew/macOS defaults/`~/.claude` from a dev/test session. `run.sh` never writes `~/.dotfiles` unconditionally: `DIR` (computed at the top from `BASH_SOURCE[0]`) is validated immediately after computation and the whole script aborts if it's empty or doesn't look like this repo (missing `run.sh`/`flake.nix`) - this is what an unresolvable `DIR` from a deleted/moved checkout used to write straight through to the symlink (issue #9). The actual `ln -sfn` calls (in `cmd_bootstrap_nix` and `cmd_rebuild`) go through `link_dotfiles`, which creates `~/.dotfiles` when absent, no-ops when it already *resolves* to `$DIR` (compare resolved paths, never raw `readlink` text - a correct-but-relative or hand-restored link must not be refused), and otherwise refuses and leaves it untouched unless `--relink` is passed. `--relink` only ever repoints an existing *symlink*: a `~/.dotfiles` that is some other real file or directory is refused, `--relink` included, because `ln -sfn TARGET DIR` against a real directory nests a stray symlink inside it and exits 0, which would hand the switcher the wrong tree with a success status. The resolved-path comparison deliberately runs *before* that non-symlink refusal, so a checkout cloned straight to `~/.dotfiles` is a no-op rather than a refusal whose only advice would be to delete the clone - keep that ordering. Both call sites rely on `set -e` propagating that refusal to abort before any switcher runs - never wrap them in `if`/`|| true`. Never revert either guard to a bare `ln -sfn "$DIR" ~/.dotfiles` - that line, run from any throwaway checkout (a worktree, a CI/validation sandbox), is what hijacks or corrupts the live machine's `~/.dotfiles` and everything that resolves through it. **Never run `run.sh`, or any test that reaches it, against a real `$HOME`** - `run.test.sh`'s new `validate_dir`/`link_dotfiles` tests demonstrate the pattern (override `cd`/`dirname` as shell functions before `source`-ing to exercise the top-level `DIR` computation, point `HOME` at a scratch dir for the symlink-write tests).
- GitHub Codespaces is a fourth and fifth host - personal and work *posture*, script-only: GitHub auto-clones this repo and runs `install.sh` (the first name it checks in its fixed setup-script filename list) fully non-interactively; it requires `CODESPACES=true` and never goes through `run.sh`'s menu. Posture is decided structurally by `detect_posture` (the workspace repo's owner vs. this repo's own `origin` owner; anything else, including undeterminable, = the locked-down work default), and `install.sh`'s `main()` dispatches to `main_personal` or `main_work`. The invariants to know before touching this area: **personal posture is Nix + home-manager, unchanged** (Determinate installer, then `flake.nix`'s `homeConfigurations."codespace-personal"` = `modules/core.nix` + `modules/codespace.nix`); **work posture never installs Nix and never clones a repository** - it delegates entirely to `work/codespace-bootstrap.sh`, which installs via apt first, npm second, and a direct release-binary download last, each step gated on `command -v`/`dpkg -s`. Don't restate the rest here: `README.md`'s "GitHub Codespaces" section owns the user-facing description of both postures (including which Claude settings file and `cc` alias each gets, and why the now-unapplied `homeConfigurations.codespace-work` stays in `flake.nix`), and `work/codespace-bootstrap.sh`'s own header and per-function comments own the mechanism detail (the `install_binary_tool` errexit suspension and how each `install_*` catches its own failures, `apt_update_once`'s memoized exit status plus `install_gh`'s deliberately scoped exception to it, the `install_gh` keyring temp-file handling, the `curl` presence gate, the `PATH` export, `RUFF_NO_MODIFY_PATH`).
  - Verify the decision logic with `bash install.test.sh` and the work-posture install steps with `bash work/codespace-bootstrap.test.sh` (both hermetic - no Nix/apt/network); verify the real install with `bash install.container-test.sh`, a disposable `ubuntu:24.04` container run wired into CI at `.github/workflows/install-container-test.yml`. Two things about that container test its own comments don't cover: it seeds the container via `git bundle create ... HEAD`, so **any local edit must be committed before a local run exercises it** (an uncommitted change silently tests the last commit instead - no error, just the wrong code path); and on an Apple Silicon dev machine the *personal*-posture Nix assertions fail for an unrelated, pre-existing reason - Nix's own build sandbox hits `unable to load seccomp BPF program: Invalid argument` under `--platform linux/amd64`'s QEMU translation, `sandbox = false` included - which is not a bug to chase, since the identical logic passes natively and on CI's x86_64 runners. Work-posture assertions involve no Nix build sandbox, so a local Apple Silicon run still meaningfully verifies the no-Nix path.
- `set -e` pitfall specific to this repo's scripts: a bare `[ cond ] && cmd` (not wrapped in `if`) that evaluates false is normally harmless mid-script, but if it's the *last* command a script executes (e.g. the final line of a function called last in `main`), its exit status becomes the whole script's exit status - so it silently fails even though every step succeeded. Use `if`/`fi` for any such check that could run last.
- Every PR gets a cheap independent check floor via `.github/workflows/ci-floor.yml` (shellcheck, this repo's hermetic test suites, `nixfmt --check`, and an eval-only `nix eval` of each host's toplevel/activationPackage drvPath, one explicit step per host so none can be silently skipped - see the comment above the `nix:` job for why this isn't `nix flake check`, which doesn't recognize `darwinConfigurations`/`homeConfigurations` at all under upstream Nix) - runs alongside, not instead of, `install-container-test.yml`. `run.test.sh`, `install.test.sh`, and `work/codespace-bootstrap.test.sh` run on `ubuntu-latest` (pure bash logic, no macOS dependency, no Nix/apt/network); `work/bootstrap.test.sh` and `herdr-agent-handoff-marker.test.sh` run on `macos-latest`, since their `#!/bin/sh` shebang is a genuinely different shell per OS (dash on Linux, bash-as-`sh` on macOS) even though every external command they touch is mocked. Any suite invoking `run.sh` (directly or via sourcing its `cmd_*` functions) must run with a scratch `HOME` set at the job/step level, not just rely on the runner being disposable - `run.sh` historically did an unconditional `ln -sfn "$DIR" ~/.dotfiles` (issue #9, since fixed by the `link_dotfiles` guard described above), and the workflow-level scratch `HOME` is defense in depth so an invocation under `act` or a future non-disposable runner stays safe even if that guard regresses.
